# 선행 사례가 v4 설계의 뼈대를 뒷받침한다

결론부터 말하면, v4의 핵심 구조인 "LLM은 목표만 추출하고, 스킬의 조건·결과로 플래너가 순서를 만들고, Runner가 스텝마다 조건을 확인하며 실행·기록한다"는 문헌과 오픈소스 양쪽에서 가장 강한 근거를 가진 설계다. 같은 GPT-4를 쓴 LLM+P 실험에서 LLM이 계획을 직접 짜면 성공률이 0~35%였지만, 목표만 번역하고 고전 플래너가 계획하면 85~95%로 올라갔다 ([LLM+P](https://arxiv.org/html/2304.11477)). 스킬의 사전·유지·사후 조건과 세계 모델에서 계획 도메인을 자동 생성하는 구조는 SkiROS2가 이미 정립했다 ([SkiROS2](https://arxiv.org/abs/2306.17030)). 반면 GitHub에는 우리와 거의 같은 스택(M0609 + RG2 + ROS 2 Jazzy + "hello rokey" 웨이크워드 + Whisper + GPT-4o/LangChain)을 쓴 학생 프로젝트가 있고, 서랍을 열어 물건을 찾는 M0609 프로젝트도 있다 ([voice-controlled-kit-assembly](https://github.com/mi1nn/voice-controlled-kit-assembly), [Seek6D](https://github.com/seb000423/Seek6D)). 따라서 "음성으로 M0609가 서랍에서 물건을 찾는다"는 것 자체는 차별점이 아니다. 차별점은 이 프로젝트들이 모두 상태 머신이나 YAML에 순서를 하드코딩한 반면, 우리는 온톨로지의 조건·결과에서 순서를 도출하고 스텝별 조건 확인 결과와 전후 상태를 기록한다는 점에 있다. 남은 리스크는 소프트웨어보다 실물과 맞닿는 부분에 몰려 있다. 서랍 닫힘을 힘 조건만으로 판정하는 현재 설계, 얇은 물체 파지, RealSense 뎁스 오차, 그리고 Isaac Sim 트윈이 접촉·힘을 검증하지 못한다는 한계가 그것이다. 마지막 장에 계획서에 바로 반영할 권고를 표로 정리했다.

## 같은 스택의 프로젝트는 이미 있다: 차별점은 "목표 → 플래너" 층

가장 먼저 확인할 사실은 **우리 하드웨어·소프트웨어 조합이 새롭지 않다**는 것이다. `mi1nn/voice-controlled-kit-assembly`는 M0609 + OnRobot RG2, Ubuntu 24.04 / ROS 2 Jazzy, MoveIt 2 위에서 openWakeWord "hello rokey" → Whisper API → LangChain 기반 GPT-4o로 품목과 수량을 추출하고, 추출 결과를 가용 키트 목록과 대조해 검증한다. 실행은 "명령 → 관측 → 실행 → 검사 → 보고" 상태 머신이 맡고, OctoMap 충돌 검사, 금지 구역(keep-out box), 파지 각도 제한, 작업 후 기대 부품과 검출 부품을 비교하는 사후 검사를 둔다 ([GitHub](https://github.com/mi1nn/voice-controlled-kit-assembly)). `seb000423/Seek6D`(M0609, ROS 2 Humble)는 우리 1막과 가장 비슷하다. GPT로 물체 이름을 고정된 검출 클래스로 정규화한 뒤, DB의 마지막 위치 확인 → 미리 정한 구역 탐색 → 서랍·상자를 열어 내부 확인 → GroundingDINO 검출 → 6D 자세 추정 → MoveIt 2 파지 순서를 고정 시퀀스로 수행한다 ([GitHub](https://github.com/seb000423/Seek6D)). `sungyu-sung/doosan_voice_ws`는 LLM 없이 `keyword_map.yaml`로 문장을 명령에 매핑하는 교육용 작업 공간으로, 우리 규칙·별칭 폴백과 같은 구조다 ([GitHub](https://github.com/sungyu-sung/doosan_voice_ws)). 범용 ROS LLM 에이전트인 NASA JPL ROSA와 Auromix ROS-LLM은 LLM이 ROS 도구를 직접 호출하게 하지만, README에 심볼릭 검증이나 실행 안전 장치는 문서화되어 있지 않다 ([ROSA](https://github.com/nasa-jpl/rosa), [ROS-LLM](https://github.com/Auromix/ROS-LLM)).

이 비교에서 우리가 정당하게 주장할 수 있는 차별점은 세 가지다. 첫째, M0609 선행 프로젝트들은 작업 순서를 코드나 YAML에 고정했지만 **우리는 스킬의 `pre`/`effect`에서 BFS로 순서를 도출**하므로 "지갑을 아래 서랍에 넣어 둬" 같은 새 목표에 새 분기가 필요 없다. 둘째, ROSA·ROS-LLM과 달리 **우리 LLM은 액추에이터를 절대 직접 호출하지 않는다**. 셋째, 서랍 열림·그리퍼·물품 위치를 명시적 상태로 두고 **스텝마다 조건 확인 결과와 전후 상태 차이를 기록**한다. 반대로 "스킬 모델링 자체"는 새롭지 않다. 산업계에는 Capability(무엇을)와 Skill(어떻게 실행)을 구분하는 CaSk/CaSkMan OWL 온톨로지가 있고 ([CaSkMan](https://github.com/CaSkade-Automation/CaSkMan)), SkiROS2는 CORA 표준 어휘를 재사용한다 ([SkiROS2](https://arxiv.org/abs/2306.17030)). 다만 표준화된 JSON-LD 로봇 스킬 스키마는 찾지 못했다. 그러므로 발표에서는 "SkiROS2·CaSk를 개념적 기반으로 삼아, 학생 규모로 가볍게 만든 JSON-LD 구현"이라고 위치를 잡는 것이 정직하고 방어하기도 쉽다.

## LLM은 목표만 내고 순서는 플래너가: 문헌이 가장 강하게 지지하는 선택

v4 6.4·7.7의 "LLM은 목표 상태만 출력" 원칙은 LLM+P의 축소판이다. LLM+P에서 GPT-4(temperature 0)가 계획을 직접 쓰면 **Blocksworld 15%, Grippers 35%, Storage 0%**였지만, 같은 모델이 PDDL 문제만 쓰고 Fast Downward가 풀면 **각각 90%, 95%, 85%**였다. 논문이 꼽은 LLM 계획의 실패 원인은 사전 조건 추론 실패, 상태 추적 실패, 그리고 계획이 목표에 도달했는지 알아채지 못하는 것이다 ([LLM+P](https://arxiv.org/html/2304.11477)). Xie 등도 LLM은 "계획보다 번역에 훨씬 적합하다"고 결론지었다 ([arXiv 2302.05128](https://arxiv.org/abs/2302.05128)). Kambhampati 등은 LLM이 스스로 계획하거나 자기 검증을 할 수 없으므로, 외부의 건전한 검증기와 함께 생성-검증 루프 안에 두라고 주장한다 ([LLM-Modulo](https://arxiv.org/abs/2402.01817)). 로봇 사례도 같은 방향이다. SayCan은 LLM 점수에 실행 가능성(affordance) 값을 곱해 실물 주방 101개 명령에서 계획 성공 84%를 냈다 ([SayCan](https://say-can.github.io/)). Text2Motion은 기하학적 실행 가능성 검사를 더해 장기 과제 성공률을 13%에서 82%로 끌어올렸다 ([arXiv 2303.12153](https://arxiv.org/abs/2303.12153)). 성공한 시스템에는 모두 LLM이 아닌 거부 장치가 있었고, 우리에게는 BFS 플래너가 그 역할을 한다. BFS는 적용 가능한 스킬만 확장하므로 **실행되는 순서는 구성상 항상 사전 조건을 만족**한다. LLM이 틀린 목표를 낼 수는 있어도, 닫힌 서랍에 물건을 넣는 식의 실행 불가능한 순서는 만들 수 없다.

이 설계에도 리스크가 없어지는 것은 아니고, 위치가 번역 단계로 옮겨질 뿐이다. LLM+P도 공간 추론이 필요한 도메인에서는 번역이 무너져 Floortile 0%, Termes 20%에 그쳤다 ([LLM+P](https://arxiv.org/html/2304.11477)). Xie 등도 수치·공간 추론이 필요한 목표와 프롬프트 표현 변화에 약하다고 보고했다 ([arXiv 2302.05128](https://arxiv.org/abs/2302.05128)). "아래 서랍", "두 번째 칸" 같은 한국어 공간 표현이 정확히 이 약점에 해당한다. 그래서 공간 참조는 자유 텍스트나 좌표가 아니라 `drawer_bottom` 같은 온톨로지 열거형 기호로만 받아야 한다. 또 하나 눈여겨볼 수치가 있다. **LLM+P에서 문맥 예시를 뺀 변형("LLM+P-")은 모든 도메인에서 0%**였다 ([LLM+P](https://arxiv.org/html/2304.11477)). 번역만 시키더라도 프롬프트에 한국어 발화 → 목표 JSON 예시를 1~3개 넣어야 한다는 뜻이다.

출력 형식은 "JSON 출력 강제"보다 한 단계 더 조여야 한다. OpenAI Structured Outputs(`strict: true`)는 제약 디코딩으로 스키마 준수를 보장하며, OpenAI 자체 평가에서 스키마 준수율 100%(프롬프트만 쓴 gpt-4-0613은 40% 미만)를 보고했다 ([OpenAI](https://openai.com/index/introducing-structured-outputs-in-the-api/), [Azure 블로그](https://azure.microsoft.com/en-us/blog/announcing-a-new-openai-feature-for-developers-on-azure/)). 온톨로지의 물품·장소 키를 스키마의 `enum`으로 넣으면 디코딩 단계에서 어휘가 고정된다. 여기서 주의할 함정이 두 가지 있다. 하나는 `unknown`/`clarify` 같은 탈출값이 없으면 enum 제약 때문에 범위 밖 요청에도 아무 유효한 물품을 고르게 된다는 점이다. 연구 노트는 이를 "제약에 의한 환각"이라 불렀다. 다른 하나는 v4의 `"goal": {"located_in.wallet": "drawer_bottom"}`처럼 **키가 동적인 객체는 엄격 스키마로 열거하기 어렵다**는 점이다. `[{predicate, subject, value}]` 같은 고정 키 배열로 바꾸는 편이 낫다. 엄격 모드의 정확한 지원 범위는 OpenAI 문서 페이지를 직접 확인하지 못했으므로, 현재 문서로 확인해야 한다. 스키마는 형식만 보장하고 의미는 보장하지 않으므로, 사용자는 "지갑"이라 했는데 `phone`을 고르는 경우를 막으려면 코드 검증(물품 존재, 현재 상태와 다른 목표, 계획 존재)이 여전히 필요하다. 끝으로 "유효하지만 틀린 목표"는 실행 전 확인 TTS("지갑을 아래 서랍에 넣을까요?")로 잡는다. ChatGPT for Robotics가 권하는 사용자 참여 원칙과 같은 해법이다 ([arXiv 2306.17582](https://arxiv.org/abs/2306.17582)).

## 온톨로지·Runner·로그는 SkiROS2·BT·NEEM에서 패턴만 빌린다

### 스킬 정의: PDDL을 원천으로 삼지 말고 내보낼 수 있게만

SkiROS2는 우리 7.5와 구조가 거의 같다. 스킬은 타입이 있는 파라미터와 **사전(pre)·유지(hold)·사후(post) 조건**을 가진다. 사전 조건은 시작 전에, 유지 조건은 실행 중 매 틱마다 검사하며, **사후 조건이 성립하지 않으면 스킬을 실패로 처리**한다. 조건은 관계, 속성 존재, 속성 값 비교 같은 작은 타입 레코드로 쓰고, PDDL 도메인과 문제는 세계 모델과 스킬 조건에서 자동 생성되어 "별도의 계획 도메인을 유지할 필요가 없다" ([SkiROS2](https://arxiv.org/abs/2306.17030)). 하지만 SkiROS2를 통째로 가져오기는 어렵다. ROS 2 지원은 `ros2`, `fix/ros2_jazzy_build` 같은 브랜치에만 있고, 마지막 커밋은 2024년 9월이며, README는 여전히 ROS 1을 안내한다 ([SkiROS2 README](https://raw.githubusercontent.com/RobotLabLTH/SkiROS2/ros2/README.md), [브랜치](https://api.github.com/repos/RobotLabLTH/SkiROS2/branches)). PlanSys2는 Jazzy용 2.0.18(2026-03)이 릴리스되어 있지만, PDDL 도메인과 C++ 액션 실행기, 액션별 BT XML을 써야 한다 ([index.ros.org](https://index.ros.org/r/ros2_planning_system/), [PlanSys2 BT 튜토리얼](https://plansys2.github.io/tutorials/docs/bt_actions.html)). 스킬 10개 안팎의 고정 세계에서 14일 안에 이를 도입하는 것은 절약하는 시간보다 드는 시간이 크다.

그래서 권고는 이렇다. 원천(source of truth)은 지금의 JSON-LD를 유지하되, 현재의 `pre: {"open.$drawer": false}` 형태가 이미 등호 조건의 연언(STRIPS/SAS+ 형태)이라는 점을 활용한다. 그리고 **조건을 SkiROS2처럼 `{subject, predicate, op, value}` 레코드로 표준화**해 두면 PDDL `:precondition`/`:effect`로 기계적으로 내보낼 수 있다. PDDL 내보내기 스크립트는 "호환성 증빙"으로 발표에 보여 주는 선택 산출물로 두고, 플래너는 직접 만든 BFS를 유지한다. 여기에 `hold` 조건을 추가한다. 예를 들어 `pick` 후 운반 중에는 "그리퍼 폭 > 0(물체 보유)"이 계속 성립해야 한다. 이는 강사가 말한 "세부 동작 및 성공 여부"를 가장 싸게 보강하는 방법이다. 또한 **스텝 성공의 정의를 "액션 결과 success"가 아니라 "사후 효과를 관측으로 확인했음"으로** 바꾼다. 그리퍼 폭, 서랍 변위, 재스캔 결과가 그 관측이다. 이름은 SOMA/CaSk 관례(Capability·Skill·Task·Action·Primitive·State·Failure)에 맞추면 별도 비용 없이 표준 어휘와 정렬된다 ([NEEM Handbook](https://ease-crc.github.io/soma/files/current/NEEM-Handbook.pdf), [CaSkMan](https://github.com/CaSkade-Automation/CaSkMan)). 클래스 계층(`Valuables ⊃ Key`)은 OWL 추론기 없이 10줄짜리 전이 폐포 함수로 충분하다. KnowRob/CRAM 스택은 ROS 1 래퍼, Prolog/Lisp, MongoDB 3.4 요구 때문에 14일 안에 채택할 수 없다 ([knowrob/ros](https://github.com/knowrob/ros), [NEEM Handbook §6.2.1](https://ease-crc.github.io/soma/files/current/NEEM-Handbook.pdf)).

### Runner: 자체 Runner를 유지하고 BT 의미론을 빌린다

BehaviorTree.CPP v4는 가장 완성도 높은 BT 엔진이다. Jazzy에 apt로 설치되고(4.10.0), 4.9.0(2026-02)에서 `TryCatch` 노드가 추가됐다 ([index.ros.org](https://index.ros.org/p/behaviortree_cpp/), [try_catch_node.h](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.CPP/master/include/behaviortree_cpp/controls/try_catch_node.h)). 그러나 노드를 C++로 써야 하고 공식 Python 바인딩은 확인되지 않았다. Groot2의 실시간 시각화는 **PRO 버전 전용**이다 ([Groot2 튜토리얼](https://www.behaviortree.dev/docs/tutorial-basics/tutorial_11_groot2)). py_trees(2.6.0)와 py_trees_ros(Jazzy 2.4.x)는 순수 Python이고 ROS 2 액션 클라이언트 래퍼와 스냅샷 토픽을 제공한다. 하지만 코어에 JSON/XML 로더가 없고 try/finally 노드도 없다 ([py_trees_ros Jazzy](https://docs.ros.org/en/ros2_packages/jazzy/api/py_trees_ros/), [decorators.py](https://raw.githubusercontent.com/splintered-reality/py_trees/devel/py_trees/decorators.py)). 무엇보다 **우리 `finally`는 BT.CPP의 TryCatch보다 의미가 강하다**. TryCatch는 try 블록이 실패할 때만 catch 자식을 실행하고, 중단(halt) 시에는 `catch_on_halt=true`일 때만 실행하며, 성공 시에는 정리 동작을 실행하지 않는다 ([try_catch_node.h](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.CPP/master/include/behaviortree_cpp/controls/try_catch_node.h)). 우리 LIFO 복구는 성공했을 때도 반드시 돌아야 하므로, BT로 옮기면 오히려 조립이 늘어난다. 검토한 어떤 기성 로거도 "스텝별 조건 확인 결과 + 상태 diff"를 기본으로 남기지 않는다는 점도 자체 Runner를 지킬 이유다. 이미 Python으로 있고 JSON-LD와 바로 연결되는 Runner를 버릴 이유는 없다.

리뷰어가 "왜 BT를 안 썼나"라고 물으면 아래 매핑표로 답하면 된다. 표의 오른쪽 열이 Runner에 추가할 만한 BT 패턴이다.

| 우리 DSL | BT 대응 | Runner에 빌려올 것 |
| :--- | :--- | :--- |
| `sequence` | Sequence | - |
| `if` | IfThenElse / Selector+Condition | `fallback` 블록: 대안을 차례로 시도(파지 전략 A → B → 사람에게 요청) ([BT basics](https://www.behaviortree.dev/docs/learn-the-basics/BT_basics)) |
| `while(max_iter)` | Repeat(N) / RetryUntilSuccessful(N) | 스텝별 `timeout_sec` ([Decorator 문서](https://www.behaviortree.dev/docs/nodes-library/DecoratorNode)) |
| `on_failure: retry` | Nav2 RecoveryNode | `recovery`: 실패 시 복구 스킬(그리퍼 재개방·재스캔) 후 재시도 ([Nav2 RecoveryNode](https://docs.nav2.org/configuration/packages/bt-plugins/controls/RecoveryNode.html)) |
| `for_each` | LoopNode / py_trees ForEach | 큐에서 꺼내 포트에 넣는 의미 ([loop_node.h](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.CPP/master/include/behaviortree_cpp/decorators/loop_node.h)) |
| `finally` | TryCatch(+`_post`) | 기존 의미 유지 + `on_halt` 경로 분리(E-stop·취소) |
| `pre` 확인 | `_skipIf`/`_failureIf`/`_while` | `hold` 조건 = `_while` ([pre/post conditions](https://www.behaviortree.dev/docs/guides/pre_post_conditions)) |
| `$ref` 변수 | 타입 있는 블랙보드 포트, `:=`/`=` | 스킬 입출력 키·타입 선언으로 실행 전 변수 검증 ([BT.CPP scripting](https://www.behaviortree.dev/docs/guides/scripting)) |

### 로그·DB: MongoDB를 확정하되 pymongo로 직접 쓰고, `mongo:8.0`으로 고정

로봇 실행 로그를 MongoDB에 담는 데는 확실한 선행 사례가 있다. KnowRob/NEEM은 기호적 서사(narrative)와 시계열 경험(experience)을 나누어, 데이터 종류마다 별도 MongoDB 컬렉션(`triples`, `tf`, `annotations`)에 JSON 문서로 저장하고 시간 키로 색인한다. **에피소드마다 당시 사용한 온톨로지 버전 전체를 함께 저장**하며, 실패 이름을 온톨로지 실패 클래스로 매핑하는 표를 둔다 ([NEEM Handbook](https://ease-crc.github.io/soma/files/current/NEEM-Handbook.pdf)). 상태 변화는 `{"s","p","o","since","until"}` 형태의 시간 범위 트리플로 교환할 수 있다. v4의 `runs`/`steps`/`states` 3컬렉션은 이 구조를 학생 규모로 줄인 것이므로 방향이 맞다. 다만 Jazzy에는 **유지보수되는 ROS 네이티브 MongoDB 로거가 없다**. `mongodb_store`는 ROS 1 전용이고 ([GitHub](https://github.com/strands-project/mongodb_store)), `warehouse_ros_mongo`는 Jazzy 바이너리 여부가 ROS Index 페이지마다 서로 다르다. MoveIt도 기본값을 SQLite로 옮기는 중이다 ([index.ros.org](https://index.ros.org/p/warehouse_ros_mongo/), [moveit2 #1296](https://github.com/moveit/moveit2/issues/1296)). 따라서 Runner 노드에서 pymongo로 직접 쓰는 것이 정답이다. 조인트·TF·카메라 같은 고빈도 원시 데이터는 rosbag2(Iron부터 MCAP이 기본)로 따로 남긴다. MCAP은 추가 전용 쓰기라서 비정상 종료 시에도 마지막 몇 메시지만 손상된다 ([Foxglove](https://foxglove.dev/blog/mcap-as-the-ros2-default-bag-format)).

버전은 계획서의 `mongo:7.0`도 프로젝트 기간에는 문제가 없다(지원 종료 2027-08-31). 그래도 새로 고정한다면 **`mongo:8.0`(지원 종료 2029-10-31)**이 낫다. 8.2는 이미 2026-07-31에 지원이 끝났고 9.0은 2026년 9월에 막 나왔으므로 둘 다 피한다 ([MongoDB lifecycle](https://www.mongodb.com/legal/support-policy/lifecycles)). SQLite는 서버가 필요 없다는 장점이 있지만, 중첩된 `pre_check`·`state_diff`를 JSON 문자열로 넣어야 한다. 과목 목표("DataBase 활용")와 Compass GUI 시연 효과까지 고려하면 MongoDB 확정이 합리적이다. DB 장애가 로봇 시연을 막지 않도록 `LogStore` 인터페이스 뒤에 pymongo 구현과 JSONL 폴백을 함께 두는 것이 안전하다.

## 서랍 탐색·복구·개폐: 숫자가 보여 주는 물리 리스크

### 장애물 제거 순서: "위에서부터"는 유지하되 같은 층에서는 큰 것부터

Mechanical Search(Berkeley AUTOLAB) 계열 연구를 보면 단순한 휴리스틱만으로도 충분히 높은 성공률이 나온다. 실물 300회 시험에서 **Largest-First(가장 큰 마스크부터)는 성공 94%, 평균 4.85회 동작**, 무작위는 92%, 10.87회였다. **정책 간 성공률 차이는 유의하지 않았고 차이는 효율(동작 횟수)에서 났다** ([arXiv 1903.01588](https://arxiv.org/html/1903.01588)). 실패의 85~90%는 "계획 가능한 동작 없음"(주로 통 모서리의 물체)이었고, 약 10%는 목표물을 건드리거나 함께 꺼낸 경우였다. 학습된 점유 분포를 쓰는 X-Ray는 성공률을 15% 높이고 동작 수를 17% 줄였다 ([X-Ray](https://mjd3.github.io/publications/2020-xray)). 다만 서랍 안에서 같은 로봇이 서랍을 열고 탐색하는 연구는 찾지 못했다. 가장 가까운 유사 사례는 위에서 접근하는 통(bin)과 옆에서 접근하는 선반이다.

우리 8.2의 "윗면이 가장 높은 물체부터"는 위에서 접근하는 서랍에서 물리적으로 유일하게 안전한 순서다(아래 물체를 먼저 빼면 쌓인 것이 무너진다). 따라서 이를 **안전 제약으로 유지**하고, 위에 아무것도 없는 물체가 여럿일 때만 **마스크 면적이 큰 것(목표 후보 영역을 더 많이 가리는 것)부터** 고르는 혼합 정책을 권한다. 솔직히 말하면, 서랍당 장애물이 1개인 시연 배치에서는 정책 차이가 거의 드러나지 않는다. 의미가 생기는 곳은 "배치 무작위화 10회" 지표다. 논문의 2N 예산 기준으로 보면 물품 5~8개 서랍에 `max_iter` 8은 적절하다. 측정 지표는 논문과 같게 성공률, 목표 노출까지의 평균 제거 횟수, 실패 분류(파지 불가 / 목표 교란 / 시간 초과)로 정하면 비교가 가능하다. 실패의 대부분이 벽·모서리 물체였으므로 시연 배치에서는 물품을 서랍 벽에서 RG2 손가락 폭 이상 띄워 두고, 파지 전에 계획된 손가락 부피가 목표 마스크와 겹치지 않는지 검사해 목표 교란을 막는다.

### LIFO 복구: 선례가 없으므로 직접 측정해야 한다

"기록된 배치로 장면을 되돌린다"는 문제는 Visual Room Rearrangement(CVPR 2021)나 3DGS 기반 작업 공간 리셋(2024) 같은 정립된 과제다 ([arXiv 2103.16544](https://ar5iv.labs.arxiv.org/html/2103.16544), [arXiv 2411.03706](https://arxiv.org/pdf/2411.03706)). 하지만 **기계적 탐색 뒤의 LIFO 복구 정확도를 평가한 논문은 찾지 못했다**. 우리 "복구 오차 2cm 이내" 목표는 비교 기준이 없는 자체 측정 지표다. LIFO 자체는 쌓인 물체에 정확히 맞는 순서다(마지막에 꺼낸 것이 가장 아래에 있던 것이고 가장 먼저 돌아간다). 함정은 다른 데 있다. 가벼운 서랍은 열 때마다 인출 거리가 달라지므로 **서랍 좌표계를 복구 직전에 다시 추정**해야 한다(`drawer_displacement` 반영). 장애물을 빼는 과정에서 이웃 물체가 밀렸을 수 있으므로, 원래 자리가 일부 점유되어 있으면 가장 가까운 빈 자리로 재계획해야 한다. 높이 기준은 개별 물체의 뎁스가 아니라 **현재 지지면(서랍 바닥 평면 또는 직전에 복구한 물체의 윗면)**이어야 하고, 놓을 때는 몇 mm 위에서 놓거나 힘 감시 하강을 쓴다. Huang 등은 선반 탐색에서 12개가 넘는 밀집 장면이면 빼낸 물체를 다시 쌓아 공간을 확보하는 것이 결정적이었다고 보고했다 ([arXiv 2207.02347](https://arxiv.org/html/2207.02347)). 우리 트레이 3슬롯이 `TRAY_FULL` 한계를 정한다는 점과 같은 맥락이다.

### 서랍 개폐: 닫힘 판정을 힘만으로 하면 오판한다

실세계 서랍·캐비닛 열기의 성공률은 생각보다 낮다. 상용 모바일 매니퓰레이터로 미지의 캐비닛 31개를 연 연구는 **제로샷 61%**였고, 실패의 59%가 손잡이 인식이었으며 당기는 중 손잡이를 놓치는 것이 주된 실행 실패였다 ([arXiv 2402.17767](https://arxiv.org/html/2402.17767v1)). 우리는 서랍장을 고정하고 포즈를 직접 교시하므로 인식 실패의 상당 부분이 사라진다. 그래서 90% 목표가 불가능하지는 않지만, Doosan 기반의 서랍 열기 성공률 자료는 없으므로 20회 반복 시험이 유일한 근거가 된다. 더 중요한 발견은 Doosan 매뉴얼에 있다. **`check_force_condition`은 힘의 크기만 검사하고 방향은 고려하지 않는다** ([Doosan Programming Manual V2.9.3](https://cobot-smx.jp/info/wp-content/uploads/2023/08/Doosan_Robotics_Programming_Manual_V2_9_3_v2_6_EN.pdf)). v4 8.4처럼 닫힘을 힘 조건만으로 판정하면, 서랍이 레일에 걸리거나 다른 곳에 부딪힌 것도 "닫힘"으로 오판한다. 닫힘은 **TCP 변위가 닫힘 위치(허용 오차 내)에 도달했고 동시에 밀기 축의 힘이 임계를 넘었을 때**로 정의해야 한다. 컴플라이언스는 `task_compliance_ctrl` 활성 상태에서만 `set_desired_force`가 동작한다. Doosan 예제의 기본 강성은 병진 3000 N/m, 회전 200 Nm/rad이며, `set_externl_force_reset()`(매뉴얼 표기 그대로)로 외력 센서 오프셋을 영점화한다 ([Doosan force 예제](https://manual.doosanrobotics.com/en/user-manual/3.6.0/3-e-series/try-force-command-samples), [Programming manual 3.3.0](https://manual.doosanrobotics.com/en/programming-manual/3.3.0/publish)). 각 컴플라이언스 구간 전에 툴 무게를 맞춘 상태로 영점화하고, 인출 축 외 방향은 강성을 낮춰 가벼운 서랍장이 끌려오는 것을 줄인다. 손잡이를 쥘 때는 RG2 폭 피드백으로 파지를 확인하거나, 손가락을 손잡이 뒤에 거는 훅 방식으로 당기는 대안을 준비한다.

### 얇은 물체와 뎁스 오차: 1.5cm 규칙은 옳고, 높이 기준은 바닥 평면으로

RealSense D400의 상대 뎁스 정확도는 대략 거리의 2%로, 0.3~0.8m에서 약 10mm 수준이다 ([arXiv 2311.01335](https://arxiv.org/pdf/2311.01335)). 실제 작업 거리에서 최대 3mm였다는 보고도 있다. 손목 카메라 핸드-아이 캘리브레이션은 UR10e에서 축별 1.5/1.8/0.6mm 편차가 보고됐다 ([PMC10610844](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10610844/)). 광택·반사면은 포화나 거짓 뎁스("유령 물체")를 만들고, 흰 광택 바닥에 비친 물체가 대표적인 사례다 ([RealSense 광학 필터 문서](https://dev.realsenseai.com/docs/optical-filters-for-intel-realsense-depth-cameras-d400/)). 오차를 합치면 **물체별 뎁스만으로는 두께 2~3mm 물체의 높이를 잡을 수 없다**. 따라서 v4 2.3의 "높이 1.5cm 이상" 선정 기준은 타당하다. 높이 기준은 스캔마다 한 번 맞춘 서랍 바닥 평면으로 잡고, 마스크는 침식(erode)한 뒤 최솟값 대신 하위 10% 백분위 같은 견고한 통계로 `top_z`를 계산한다. 영(0) 뎁스 픽셀 비율이 높은 마스크는 손목 각도를 바꿔 재촬영한다. 얇은 물체 파지 문헌은 손톱처럼 얇은 손끝을 물체와 바닥 사이에 밀어 넣는 방식이 주류다 ([arXiv 2608.07887](https://arxiv.org/pdf/2608.07887), [scooping 설계 연구](https://www.researchgate.net/publication/328053559_Picking_grasping_or_scooping_small_objects_lying_on_flat_surfaces_A_design_approach)). 표준 RG2로 할 수 있는 현실적인 대응은 두 가지다. 하나는 컴플라이언스 또는 힘 임계 하강으로 바닥에 닿은 뒤 약 1mm 물러나서 닫는 것이고, 다른 하나는 차키를 날이 아니라 두꺼운 머리나 키홀더 쪽으로 긴 축에 수직하게 잡는 것이다. 손끝 교체가 허용되면 3D 프린팅한 얇은 손끝 인서트가 가장 싼 해법이다. RG2의 최소 신뢰 파지 두께나 열쇠 파지 성공률 자료는 찾지 못했으므로 Day 2 파지 테스트가 유일한 근거가 된다.

## 디지털 트윈과 드라이버: 기대치를 조정할 두 지점

Isaac Sim은 ROS 2 Jazzy를 공식 지원하고 ([Isaac Sim ROS 2 설치 문서](https://docs.isaacsim.omniverse.nvidia.com/latest/installation/install_ros.html)), 실물 `/joint_states`를 트윈에 미러링하는 방식은 커뮤니티에서 흔히 쓰인다. 우리 조합과 같은 **M0609 + Isaac Sim 5.1.0 공개 프로젝트**(택배 분류)도 있다. 이 프로젝트는 doosan-robot2의 USD/URDF와 RMPflow를 썼지만, 파지는 FixedJoint로 근사했고, 공유 World에서 콜백이 섞여 태스크 상태가 혼동되는 문제를 겪었다. 저자 스스로 Isaac Sim + ROS 2 종단 간 동작은 스모크 테스트 이상 검증되지 않았고 sim-to-real은 구현하지 않았다고 밝혔다 ([parcel-sorting-isaac-sim](https://github.com/asdfzd/parcel-sorting-isaac-sim)). 이 사례가 주는 교훈은 분명하다. **트윈은 기구학·도달성·충돌·관절 한계 검사에는 믿을 만하지만, 컴플라이언스·힘, 서랍 마찰, 가벼운 서랍장의 미끄러짐, 얇은 물체 파지, RealSense 뎁스 결함은 검증하지 못한다.** v4 14장의 "사전 검증을 통과한 JSON의 실물 첫 실행 성공률 80%"는 트윈이 원리상 검증하지 못하는 실패(파지·서랍 걸림)까지 트윈의 성과로 잡게 되므로, "트윈이 거른 도달성·충돌 문제의 수"와 "명령 vs 미러링 관절 편차" 같은 트윈 고유 지표로 바꾸는 편이 정직하다. Isaac Sim 사전 검증 효과를 정량화한 공개 자료도 찾지 못했다. 반대로 LLM이 생성한 JSON(Stretch, 6.5)의 첫 관문으로는 Isaac Sim보다 **같은 STRIPS 모델로 조건·효과를 기호적으로 시뮬레이션하는 드라이런**이 더 싸고 결정적이다. 이것이 ISR-LLM과 LLM-Modulo의 검증기 패턴이다 ([ISR-LLM](https://arxiv.org/abs/2308.13724), [LLM-Modulo](https://arxiv.org/abs/2402.01817)).

두 번째로 조정할 지점은 Doosan 드라이버다. Doosan은 Jazzy용 ROS 2 매뉴얼(`DSR_ROBOT2` Python API, `DrlStart` 서비스, Virtual/Real 모드)을 제공한다 ([Doosan ROS 2 Jazzy 매뉴얼](https://doosanrobotics.github.io/doosan-robotics-ros-manual/jazzy/)). 하지만 **Jazzy에서 실물 로봇 기동이 에뮬레이터·가상 모드로 떨어지는 문제가 이슈로 보고되어 있다** ([doosan-robot2 #340](https://github.com/DoosanRobotics/doosan-robot2/issues/340)). Humble에서도 실물 M0609(DRCF v2.12)에서 controller_manager가 멈추는 이슈가 있었다 ([#309](https://github.com/DoosanRobotics/doosan-robot2/issues/309)). Day 0~1의 "DSR 드라이버로 실물 접속 확인"은 단순 연결 확인이 아니라 **실제로 Real 모드로 기동되어 실물이 움직이는지**를 판정 기준으로 삼아야 한다. 이것이 막히면 실물 핵심 경로 전체가 막힌다.

## Conclusion

이번 조사로 바뀐 판단은 "어디에 시간을 쓸 것인가"다. 소프트웨어 구조(목표만 내는 LLM, 조건·효과 기반 BFS, 자체 Runner, MongoDB 로그)는 선행 연구가 이미 정답에 가깝다고 확인해 주었으므로, 새 프레임워크를 도입하며 시간을 쓸 이유가 없다. 남은 14일의 위험은 거의 전부 실물 접촉부에 있다. 서랍 닫힘 오판, 손잡이 미끄러짐, 2~10mm 뎁스 오차, 얇은 물체, Jazzy 실물 모드 기동이 그것이며, 모두 공개된 성공률 자료가 없어 팀이 직접 측정해야 한다. 따라서 Day 2~3의 실물 시험(파지 테스트, 서랍 20회)은 확인 절차가 아니라 계획서의 숫자를 실제로 정하는 실험으로 다뤄야 한다.

발표 전략도 여기서 나온다. "음성으로 M0609가 서랍에서 물건을 찾는다"는 이미 GitHub에 있다. 강사 챌린지에 대한 우리만의 답은 **같은 하드웨어로 선행 프로젝트들이 하드코딩한 순서를, 우리는 온톨로지에서 도출하고 그 근거(조건 확인·전후 상태)를 스텝마다 DB에 남긴다**는 한 문장이다. 2막에서 플래너가 "서랍을 먼저 열어야 하고, 물건을 든 채로는 열 수 없다"를 스스로 도출하는 장면과, 마무리에서 그 판단의 근거가 DB 로그로 조회되는 장면이 이 차별점을 가장 직접적으로 보여 준다. 시연 레벨을 낮추더라도 이 두 장면만은 지켜야 한다.
