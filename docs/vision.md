[실측: PC1 덤프 158장 v2 다시 검출, main 대비] 목표·오류 코드·물체 목록·id 번호 변화 0, 3 mm 이상 내려간 25건(3.0~13.5 mm) 모두 높은 이웃 옆(판 밑·옆 지우개 보정 전 15.9~27.5 → 보정 후 12.3~17.8, 쌓인 몽키·캐러멜), 그 밖 1~3 mm 하락 15건·상승 6건(≤ 0.9 mm), `position` 변화 최대 1.0 mm, `occluded_by` `null` → `["cover_plate#1"]` 4건. 한계: 이웃에 기댄 물체는 진짜 윗면이 이웃 쪽이라 낮게 잴 수 있음(이번 덤프엔 사례 없음). 바닥 단독 물체가 1.5~3 mm 높게 나오는 것은 원점(#83) 문제라 별개.
* **분할 모델 v2 [10/12, #229 — 사용자 결정]**: 노드 기본 가중치 `models/yolo11s_seg_ready2go_v2.pt`(3단 쌓기·판 밑·립밤 자세 50장 보강, v1은 `VISION_WEIGHTS`로 되돌림). 로직으로 못 푸는 마스크 문제(판 밑 검은 립밤 미검출, 쌓인 아래 물체 마스크 번짐)를 겨냥. [실측: 덤프 54장 다시 검출] 판 밑 립밤 3/3 찾음(v1 0/3), 3단 쌓기 캐러멜 `top_z` 50.6 → 37.6~38.5 mm, 덮개 밑 지우개 `null` 2장 → 덮개, 옆 립밤 헛관계 2장 사라짐, 차키 밑 몽키 1장은 `top_z` 16.6 → 32.0 mm로 나빠짐. 학습·평가 상세는 [tools/yolo/README.md](../tools/yolo/README.md) "3단 쌓기·판 밑 보강 v2". s95 검증셋으로 epoch를 골라 낙관적일 수 있어 실물 새 촬영으로 확인
* **모델 결정**: 학습 중인 `Fruits/best.pt`는 서랍 물품과 클래스가 달라 사용하지 않음. **실물 데이터로 학습**하고, Isaac Sim Replicator 합성 데이터는 여유 시 보강용으로만 사용.
* **pose 산출 (V2)**: `position`은 YOLO 박스 중심, `position.z`는 0, `yaw`는 긴 변 방향 (−π/2, π/2] — 정의 원본은 [runner.md 7.1](runner.md). 아래는 확정 사항과 남은 `[팀 확정 필요]`이다. 남은 것은 정답 yaw 기록법(#62)과 `yaw_valid` 판정 임계값뿐이다.
  * **yaw 산출 방식 (P1 기준선, 사용자 확정 10/04)**: YOLO 박스 안에서 서랍 바닥보다 높은 뎁스 픽셀을 덩어리로 분리하고, 그 윤곽의 최소 외접 사각형(`cv2.minAreaRect`) 긴 변 방향을 yaw로 쓴다. 위에서 본 모양이 정사각형이거나 둥근 대칭 물체는 0 고정. 같은 덩어리에서 `top_z`(덩어리의 최고 높이)도 구하며, V3 미지 물체의 "뎁스 덩어리"와 같은 분리 단계를 재사용한다. 비교 실험은 데모 경로 밖으로 분리: YOLO-OBB([#62](https://github.com/Jik-Kim/ready2go/issues/62), 조장 E 합의 후 착수), SAM2 마스크([#63](https://github.com/Jik-Kim/ready2go/issues/63), FR-VIS-04, P3 선택).
  * **구조 (구현됨, [#80](https://github.com/Jik-Kim/ready2go/pull/80))**: 파일 목록은 위 V2 구현 상태 참조. 뎁스 덩어리 계산은 `core/depth_blob.py`, 대칭 판정·`yaw_valid` 결정은 `core/inspect_real.py`가 한다. 덩어리가 작거나 비정상(뎁스 결손, 너무 얇음, 명목 크기와 크게 다름)이면 yaw 0 + `yaw_valid = false`이고, 판정 임계값은 `config/vision_params.yaml`의 `depth_blob`에 있다(값은 `[팀 확정 필요]` 그대로). **제안과 다른 점**: ① yaw 추정기 인터페이스는 따로 두지 않았다 — `inspect_real.py`가 `depth_blob`을 직접 부른다. ② `compose.yaml`에 `VISION_MODE` 환경변수(yolo | yolo_sam2 | oracle)는 있으나 현재 노드가 읽지 않는다(무시됨, 항상 뎁스 덩어리). OBB·SAM2를 붙일 때 분리·선택을 구현한다([#62](https://github.com/Jik-Kim/ready2go/issues/62)·[#63](https://github.com/Jik-Kim/ready2go/issues/63)). ③ 모델 경로는 params yaml이 아니라 노드 ROS 파라미터 `weights`(기본값 `/models/yolo11s_seg_ready2go_v2.pt` — 10/11~10/12 는 `yolo11s_seg_ready2go_v1.pt`, 그 전에는 `yolo11n_ready2go_v1.pt`, 실행 때 바꿀 수 있음)다. 신뢰도 대신 `yaw_valid`만 `result_json`에 내보내는 것은 제안대로다.
  * **정답 yaw 기록 `[팀 확정 필요]`**: 비교 실험이 공정하려면 같은 이미지에 정답 yaw가 필요하다. 촬영 때 기록하는 방법(각도 지그 또는 격자 시트)은 #62에서 정한다. 자리표시로 `capture_session.py --gt-yaw-method`가 `session.yaml`에 방법을 남긴다.
  * **대칭 물체 판정 (확정, PM 제안·사용자 승인 10/04)**: 온톨로지 `size_m`의 가로·세로 두 값의 max/min 비가 기준값(`pose_rules.SYMMETRY_RATIO`, 숫자는 이 상수 한 곳에만 둔다) 미만이면 대칭 물체로 보고 yaw를 0으로 고정한다(`pose_rules.is_symmetric`). 새 온톨로지 필드는 만들지 않아 계약 변경이 없다. 비율은 측정한 덩어리가 아니라 명목 `size_m`으로 계산하고(재현성) 높이(`size_m[2]`)는 쓰지 않는다. 확정 11종에서는 `masking_tape`(1.0)만 해당하고 다음은 `cover_plate` 1.33·`airpods_case` 1.34라 경계가 분명하다. 예외 물품이 생기면 그때 `world.jsonld` items에 한 곳만 추가한다.
  * **`size_m` 규약**: 정의는 [ontology.md](ontology.md)의 "치수 계약" 한 곳([긴 변, 짧은 변, 높이], #46). 이 문서와 다른 문서는 링크만 둔다.
  * **`yaw_valid` (B 요청, 사용자 승인 10/04)**: `pose`에 bool 필드. 대칭 물체와 정상 산출은 `true`, 덩어리 비정상(뎁스 결손·너무 얇음)은 `false`(yaw는 0 자리표시). 얇은 물체(지우개·차 키)가 폴백에 가장 자주 걸리는데 둘 다 yaw가 필요해서, 진짜 0°와 "모름"을 구분해야 한다. 정의: [runner.md](runner.md) 7.1.
  * **갈라진 마스크 조각으로 yaw (10/14, 분할 모델만)**: 위에 얹힌 물체가 긴 물체(몽키) 가운데를 덮어 분할 마스크가 둘 이상으로 갈라지면, 가장 큰 뎁스 덩어리만으로는 명목 길이의 ±`size_tolerance` 밖이라 `yaw_valid = false`였다. 그러면 B 가 방향을 모르는 물체를 외접원으로 막아 서랍 빈 자리가 사라졌다(10/14 PC2 S1 `RESTORE_INCOMPLETE`·트윈에서 `NO_FREE_SPACE`, #196·#337). 이제 가장 큰 덩어리가 길이 검사에 떨어지고 **넓이 `depth_blob.fragment_min_area_ratio` 이상 조각이 2개 이상**이면(0 이면 끔), 마스크 조각 전체를 `top_z`/2 평면에 투영한 최소 외접 사각형으로 yaw 를 잰다 — 긴 변이 명목 ±`fragment_size_tolerance`, 짧은 변이 명목 짧은 변의 (1 + `fragment_size_tolerance`) 이하일 때만(덩어리 검사 `size_tolerance` 보다 좁게 — 방향이 틀린 채 true 가 되면 B 가 실제 물체 위를 빈 자리로 볼 수 있음) `yaw_valid = true`(덤프 판단 근거 `yaw_reason` "마스크 조각 전체로"). 한 조각만 보이는 물체(판 밑에 일부만 보이는 지우개 등)는 방향이 애매해 그대로 `false`. [실측: PC1 실물 덤프 110장(분할 마스크) main 대비 재계산] 바뀐 것은 가운데가 덮인 몽키 19장의 `yaw_valid` false → true 뿐(위치·`top_z`·가림 관계·목표·오류 변화 0). 10/14 S1 덤프 두 장은 다 보인 뒤 덤프(−0.2°)와 0.6°·0.2° 차이. 결과 형식 변경 없음, `vision_params` 에 `fragment_min_area_ratio`·`fragment_min_px`·`fragment_size_tolerance` 추가(해시 바뀜, 값은 [`config/vision_params.yaml`](../config/vision_params.yaml) `depth_blob` 이 원본). 갈라진 몽키 19장의 조각 외접 사각형은 긴 변 169~175 mm(명목 170)·짧은 변 56~63 mm(명목 61).
  * **투영 높이 평면 (확정, B 의견 채택·사용자 승인 10/04)**: 박스 중심 픽셀을 서랍 좌표 x·y로 옮길 때 `z = top_z/2` 평면과 교차시킨다(그리퍼가 대략 물체 높이 절반에서 닫힘). 거의 수직인 `drawer_top_view`에서는 평면 선택에 따른 오프셋 차이가 작아 AC-VIS-01(1.5 cm)에 큰 영향이 없다. `top_z`는 같은 뎁스 덩어리에서 얻으므로 순환 의존이 없다.
  * **머리 방향(망치·스패너·당근 펜)**: P1에서는 제공하지 않는다. B의 파지 시험에서 필요하다고 하면 `result_json` 확장(계약 변경)으로 별도 요청한다.
* **서랍 높이**: 새 서랍은 처짐이 없다(`config/places.yaml`의 `sag_m_at_max_travel` = 0 [실측 A 10/03]). 그래도 얇은 물품은 뎁스 오차 몇 mm로 물체와 바닥이 구분되지 않을 수 있으므로 높이는 서랍 바닥 기준(힘 감지, [domain.md 8.5](domain.md))으로 잡고 비전은 x·y를 쓴다.

  * **그림**: 그 요청에 쓴 컬러 프레임에서 서랍 안쪽(`places.yaml` `interior_m` 투영 + 여백)만 잘라 16:9 로 키운 1280×720 JPEG(작은 칸에서도 글씨가 보이게, 서랍 투영이 안 되면 전체 화면 — 픽셀 좌표는 카메라 영상과 다름, 잘라내기·오류별 발행·영문 키 대체·`#n`·KST 표시는 #357 승인 범위). 물체마다 분할 마스크(박스 모델이면 상자)·이름·신뢰도, 결과에 있는 물체는 **윗면 높이**(`top_z`)·**가리는 물체**(`occluded_by`, 빈 목록이면 "가리는 물체 없음", `null` 이면 표시 안 함)·`yaw_valid: false` 면 "방향 모름", `true` 면 긴 축 방향 선. 같은 종류가 여럿이면 이름 뒤에 결과 id 번호(`#1`·`#2`), 결과에 없는 검출(서랍 밖 제외·같은 종류 중복 병합)은 마스크·이름·신뢰도만. 위쪽 띠에 서랍 칸·찾는 물건·촬영 시각(`header.stamp` 를 **KST** 로 표시 — stamp 자체는 UTC 에포크)·실패 요청이면 오류 코드. 결과 JSON 의 의미를 바꾸거나 새 판단을 하지 않는다. 예시: [`images/vision_inspect_overlay_example.jpg`](images/vision_inspect_overlay_example.jpg) — 10/14 PC2 S1 덤프와 그 촬영 때 노드 결과(`result_json`)로 A 그림 코드가 그린 것(한글 글꼴 사용, 노드는 아래 글꼴 규칙).
  * **발행 조건**: 컬러 프레임을 받은 요청마다 성공·실패 모두 최대 1장, 실패 요청은 위쪽 띠에 오류 코드 — `REGION_NOT_VISIBLE`·`DEPTH_INVALID`·`RESULT_INVALID` 는 검출까지 그림(결과 필드 없음), `TF_UNAVAILABLE` 은 검출 전이라 **검출 없이 사진만**(잘라내기 없이 전체 화면, 그리기용으로 검출을 다시 돌리지 않음). 프레임 전 오류(`UNKNOWN_REGION`·`CAMERA_TIMEOUT`), `CONFIG_INVALID`·`STUB_NOT_READY`, 스텁 노드는 사진 없음.
  * **생략(보장 아님)**: 그리기·JPEG 인코딩·발행 실패(경고 로그만), 아직 그리지 않은 요청이 더 새 요청으로 바뀐 경우, 이미 발행한 사진보다 촬영 시각이 오래된 경우.
  * **처리**: `InspectRegion` 응답을 막지 않는다 — 노드는 그릴 재료만 넘기고 응답하며, 별도 작업 스레드 하나가 가장 최근 요청 하나만 보관해 그리고 발행한다. 실패해도 서비스 응답·인식 결과에 영향 없음.
  * **소비자(웹) 규칙**: 촬영 시각(`header.stamp`)과 웹 수신 시각을 따로 보관하고 화면에는 촬영 시각을 표시(늦게 접속해 `TRANSIENT_LOCAL` 로 받은 지난 사진도 촬영 시각 그대로). 캐시보다 촬영 시각이 오래된 메시지는 무시. 사진이 오래됨과 카메라 연결 끊김(`/wrist_cam/color/camera_info` 기반 `/api/status` `camera`)은 따로 판단 — "오래된 사진" 시간 기준은 토픽 계약이 아닌 웹 설정값(D, 합의 후).
  * **이름 표시 글꼴**: 비전 이미지에 한글 글꼴이 없으면 클래스 키(영문)로 그린다. `docker/vision/Dockerfile` 에 `fonts-nanum` 을 넣어 이미지를 다시 빌드하면 한글 이름(빌드 전 이미지는 영문).
