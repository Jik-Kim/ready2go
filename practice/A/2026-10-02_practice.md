## 1. 하드웨어·환경 트러블슈팅

### 1.1 RealSense `Left MIPI error`
- **증상**: ROS 노드는 `RealSense Node Is Up!`까지 정상인데 1초 뒤 `Hardware Notification: Left MIPI error` 경고.
- **원인 판단**: 소프트웨어가 아니라 좌측 IR 이미저 링크의 하드웨어/전기적 문제. 로그 순서(노드 정상 기동 → 직후 경고)와 USB 인식은 정상이라는 점에서 케이블·포트·전원 쪽으로 좁힘.
- **조치**: USB 3.0 포트 직결 + 재연결.
- **결과**: 재연결 후 경고 없이 기동, 이후 컨테이너 기동에서도 재발 없음 [실측].
- **배운 점**: 로그의 "정상 기동" 다음 줄을 끝까지 읽는다. 하드웨어 경고는 소프트웨어 설정으로 풀려고 하지 않는다.

### 1.2 `cv2.VideoCapture`가 카메라를 못 여는 문제 (2단계)
1. **카메라 ID 혼동**: `/dev/video6`은 RealSense의 **IR(흑백)** 스트림이었다. `v4l2-ctl --list-devices`와 `--list-formats`로 확인해 RGB는 `/dev/video8`(YUYV)임을 확인 [실측]. 같은 장치에 노드가 4개 이상(Depth/IR/RGB/메타데이터)이라 번호만으로 추측하면 안 됨.
2. **장치 독점**: ID를 맞춰도 실패. `fuser -v /dev/video8`로 `realsense2_camera_node`가 장치를 잡고 있음을 확인 [실측]. 카메라는 한 프로세스만 열 수 있다.
- **결론**: ROS 노드를 끄고 직접 열거나, 노드를 켠 채 **토픽을 구독하는 방식으로 통일**. `/dev/videoN` 번호는 재연결 시 바뀌므로 코드에 하드코딩하지 않는다.

### 1.3 Docker 컨테이너에서 `cv2.imshow` 실패
- **증상**: `qt.qpa.xcb: could not connect to display :0`.
- **원인**: 컨테이너의 `DISPLAY=:0`이었지만 호스트의 X 소켓은 `/tmp/.X11-unix`에 `X1`, `X2`뿐. 호스트 `Xorg/Xwayland` 프로세스 확인 결과 실제 디스플레이는 Xwayland `:1` [실측].
- **해결**: 호스트에서 `xhost +local:root`, 컨테이너에서 `export DISPLAY=:1`.
- **배운 점**: `DISPLAY` 값은 세션마다 다를 수 있다. 컨테이너를 만들 때 `-e DISPLAY=$DISPLAY`로 호스트 값을 넘긴다. 이후 `docs/docker.md`의 운영 규칙에 반영.

### 1.4 ROS 2 Python 패키지 `realsense_subscriber`
- **오류**: `setup.py`의 `entry_points`가 `realsense_subscriber.realsense_img:main`을 가리켰는데 실제 파일은 `subscriber_img.py` → 실행 시 `ModuleNotFoundError` 예정이었던 것을 빌드 전에 발견.
- **형식 정리**: `'실행명 = 패키지.모듈명:함수명'` — 모듈명은 파일명(`.py` 제외)과 일치해야 한다.
- **의존성**: import(`rclpy`, `sensor_msgs`, `cv_bridge`, `cv2`) 기준으로 `package.xml`에 `python3-opencv`가 빠져 있음을 확인. 시스템 패키지로 표현해야 하며 pip 이름(`opencv-python`)은 rosdep에서 동작하지 않는다.
- **결과**: `colcon build` → `source install/setup.bash` → `ros2 run` 정상 동작 확인.

## 2. 설계 검토

### 2.1 기획서 검토 → Docker·음성 필수 요건 반영
초기 기획서를 읽고 지적한 핵심:

| # | 지적 | 이유 |
| :--- | :--- | :--- |
| 1 | JSON 시퀀스가 선형이라 Unpacking(조건·반복)을 표현 못 함 | 오클루전 탐색은 "안 보이면 하나 꺼내고 다시 촬영"의 반복. 변수(`$ref`)·`if`·`while`·`finally` 필요 |
| 2 | 동작명·파라미터명이 문서 안에서 불일치 (`approach_vector` vs `approach_offset`, `move_pose` vs `move_to_named_pose`) | 규격서를 단일 기준으로 통일하지 않으면 구현에서 깨짐 |
| 3 | 로그 예시의 합계 수치가 맞지 않음 (스텝 합 ≠ 총 소요시간, 스텝 하나에 `duration_sec` 없음) | 로그가 핵심 산출물인데 예시부터 틀림 |
| 4 | 복구 좌표를 월드 기준으로 저장 | 서랍 개방 거리가 달라지면 어긋남 → 서랍 로컬 좌표 |
| 5 | 장애물 선택 정책·트레이 용량 처리가 없음 | "무엇을 먼저 꺼내는가"가 빠져 있음 |
| 6 | "온톨로지"가 사실상 조회 테이블 | 클래스 계층·속성·한국어 별칭을 넣어야 플래너·음성 파서가 실제로 사용 |
| 7 | 일정 과적재, 버퍼 없음, 음성(STT) 일정 누락 | Day 1에 스키마·서랍 물리·ROS 인터페이스를 한꺼번에 배정 |

## 3. 구현·검증: `realsense` 컨테이너 (#5)

### 3.1 발견한 버그와 정정한 추정
| 항목 | 내용 |
| :--- | :--- |
| `/config` 마운트 누락 | `compose.yaml`의 `realsense` 서비스만 `./config`를 마운트하지 않아, `CYCLONEDDS_URI=file:///config/...`가 가리키는 파일이 컨테이너에 없었음. 다른 서비스와 비교해서 발견. 마운트 추가 후 `/config`에 파일 확인 [실측] |
| 토픽 경로 | Dockerfile 주석에 "`__node:=wrist_cam`만 주면 `/wrist_cam/...`으로 발행"이라고 [추정]되어 있었으나, **실측 결과 `/camera/wrist_cam/...`** 였다. 변형 2개를 시험해 `-r __ns:=/`를 함께 줘야 `/wrist_cam/...`으로 나옴을 확인하고 주석을 [실측]으로 정정 |
| 불필요한 스트림 | IMU(accel/gyro), 적외선 2채널은 쓰지 않으므로 비활성화(USB 대역폭 절약) |

### 3.2 검증 결과 [실측]
| 항목 | 결과 |
| :--- | :--- |
| 컬러 `/wrist_cam/color/image_raw` | 29.99 Hz |
| 정렬 뎁스 `/wrist_cam/aligned_depth_to_color/image_raw` | 29.98 Hz, `16UC1`, 컬러와 같은 해상도 1280, `frame_id=wrist_cam_color_optical_frame` |
| `vision` 용도 컨테이너에서 수신 | 컬러·정렬 뎁스·`color/camera_info` 모두 수신 |
| `cv_bridge` | numpy 1.26.4, cv2 4.9.0 조합에서 import 정상 |
| GPU | `torch 2.11.0+cu128`, RTX 5060 (compute capability 12.0)에서 `cuda.is_available()=True` |

### 3.3 판단: 새로 빌드하지 않고 기존 컨테이너 재사용
`vision` 이미지를 새로 빌드하다가(`torch`·`ultralytics` 수 GB 다운로드), 사용자가 이미 같은 환경(GPU까지)을 갖춘 컨테이너를 쓰고 있음을 짚어 빌드를 중단했다. 기존 컨테이너에서 버전을 읽어 Dockerfile에 고정하고, **새로 빌드한 이미지는 검증하지 않았다**고 파일에 명시했다.
- **미확인**: RTX 4060(PC2)에서의 동작.

## 4. 설계 결정: 손목 카메라 TF 구조

- **발견**: realsense 드라이버가 `/tf_static`으로 카메라 내부 프레임 트리를 이미 발행한다 [실측].
  ```
  wrist_cam_link ─ wrist_cam_color_frame ─ wrist_cam_color_optical_frame
                └ wrist_cam_depth_frame ─ wrist_cam_depth_optical_frame
  ```
- **문제**: TF에서 한 프레임은 부모를 하나만 가질 수 있다. 핸드-아이 캘리브레이션 결과를 `link_6 → wrist_cam_color_optical_frame`에 직접 걸면 드라이버가 이미 정한 부모와 충돌한다. 또 ICD의 프레임 이름(`wrist_cam_optical`)이 실제 `frame_id`와 달랐다.
- **선택지**: A안(`link_6 → wrist_cam_link`에 걸고 `T_gripper2camera`를 변환), B안(드라이버 TF 끄기), C안(이름만 변경).
- **결정**: A안. 드라이버의 `link → optical` 변환은 공장 캘리브레이션 값이라 그대로 쓰는 게 정확하고, 팀 구조(bringup은 static TF 1개만 발행)에도 맞는다. PM 세션에 물어 같은 결론을 확인했다.
- **계산식**: `T_link6→cam_link = T_link6→color_optical(핸드-아이) × (T_cam_link→color_optical)⁻¹`
- **#7 시작 전 확인 항목** (PM 지적): ① 캘리브레이션 시 TCP 설정(`link_6` 기준인지) [추정, 미확인], ② `dsr01` 네임스페이스에서의 `link_6` 실제 이름, ③ `posx` 단위(mm, ZYZ 오일러각).
- **상태**: C 확인 대기 (결정 로그 #23, "미결 (제안)").

## 6. 배운 점

1. **[추정]은 검증 전까지 [추정]이다.** Dockerfile 주석의 토픽 경로 추정이 실제와 달랐다. 문서에 추정을 쓸 때는 검증 방법을 같이 적고, 검증 후 즉시 정정한다.
2. **같은 구성을 가진 다른 서비스와 비교하면 버그가 보인다.** `/config` 마운트 누락은 `vision` 서비스와 나란히 놓고 봐서 발견했다.
3. **계약(ICD)과 실제가 어긋나면, 비용이 적은 쪽을 바꾼다.** 토픽은 remap 한 줄로 계약에 맞추고(비용 0), 프레임 이름은 드라이버가 만드는 실제 이름에 계약을 맞췄다.
4. **의존 관계는 "정말 필요한가"를 묻는다.** #14의 선행에서 캘리브레이션을 뺀 것처럼, 불필요한 선행은 일정을 막는다.
5. **여러 세션이 한 폴더를 쓸 때는 편집 주체를 정한다.** 문서는 한 세션이 쓰고 다른 세션은 내용만 전달하는 방식으로 충돌을 피했다.
6. **범위 판단은 최신 문서를 다시 읽고 한다.** SAM2는 처음 답한 뒤 최신 계획서(실물 + 손목 카메라)를 읽고 영상 트래킹 비권장으로 판단을 고쳤다.
