## 1. 서랍 좌표계로 트윈 씬 재생성

- B의 3점 터치 결과(`config/places.yaml` `drawer_top.tf`, 최대 인출 `tf_at_travel_m`)를 `build_scene.py`가 읽도록 했다. 값이 `null`이면 기존 임시 배치를 쓰고, tf만 있고 인출 거리가 없으면 오류로 멈춘다. `verify_scene.py`는 최대 인출 상태의 서랍 좌표계가 tf와 1 mm·0.1° 이내로 일치하는지 검사한다 (PR #55).
- 닫힘 위치는 원점에서 서랍 x축으로 `tf_at_travel_m`만큼 뒤로 간 점으로 계산한다(순수 파이썬 `_dims.py`, 단위 테스트).
- 첫 재생성에서 **서랍장이 작업대에서 약 23 cm 떠 있었다**. x·y는 평면도 줄자 배치와 2 mm 안쪽으로 맞았고 z만 어긋났다 [실측].

### 1.1 원인 추적: z가 TCP 오프셋만큼 높음
- 어긋난 양 0.2268 m가 TCP 오프셋 228 mm(`calibration_meta.yaml`)와 1.2 mm 차이였다 [계산]. "측정 당시 활성 TCP가 없었다"는 가설을 세웠다 [추정].
- 로봇이 수직 아래를 보는 자세라 TCP 오프셋은 z에만 들어가고 x·y는 영향이 없다 — x·y만 맞고 z만 틀린 증상과 일치했다.
- 사용자가 펜던트를 직접 확인해 TCP와 tool weight가 둘 다 풀려 있었음을 확인했다 [사용자 확인]. B가 z에서 228 mm를 빼는 정정(PR #58)을 올렸고, 재생성 후 서랍장이 작업대에 놓였다 (원점 [0.3838, −0.4597, 0.004] m).

## 2. `inspect_region` pose 계약 확정

사용자·B·PM·E·C 합의 (이슈 #18, PR #61·#65·#66).

| 항목 | 확정 |
| :--- | :--- |
| `position` | YOLO 박스 중심의 서랍 좌표 x·y, `position.z` = 0 (높이는 `top_z`에만) |
| `yaw` | 긴 변 방향, 범위 (−π/2, π/2]. 위에서 본 모양이 정사각형이거나 둥근 물체(`size_m` 가로·세로 비 기준)는 0 |
| `yaw_valid` | bool. 대칭·정상 산출은 true, 덩어리 비정상(뎁스 결손·너무 얇음)은 false이며 yaw는 0 자리표시 |
| 투영 평면 | 박스 중심 픽셀을 `z = top_z/2` 평면과 교차 |
| yaw 산출(P1) | 서랍 바닥 위 뎁스 덩어리 윤곽의 `cv2.minAreaRect` 긴 변. YOLO-OBB(#62)·SAM2(#63)는 데모 경로 밖 비교 실험 |

- 코드: `ready2go_vision/core/pose_rules.py`(정규화·검증), `tools/validate_contracts.py`가 예시 JSON의 z = 0, yaw 범위, `yaw_valid`를 검사한다. 스텁은 `yaw_valid`가 bool이 아니면 `CONFIG_INVALID`로 실패한다(문자열 "false"가 참으로 읽히는 문제를 PM 리뷰로 발견).
- 리뷰에서 배운 것: D의 P1 지적("자리표시자 yaw 0을 진짜 0°로 쓰면 밀기 방향이 틀림")이 맞았다. 실제 연동(수신 측 차단)은 B의 #66이 먼저 머지된 뒤에 #65를 머지하는 순서로 해결했다.
- **검증 범위를 나눠 적었다**: 형식 테스트(완료)와 Day 5 `inspect_region` 실제 구현·#10 Runner 연동(미검증).

## 4. 로봇 자세 분석: 높이·각도 변경 포즈

- `jog_gui`의 Z `−`를 눌렀더니 한 번에 Z −8 mm와 함께 X +5 mm, Y −3.5 mm로 비스듬히 움직임 [실측]. 같은 방향으로 반복됐다.
- 로봇 모델(`m0609.urdf`)로 순기구학을 계산했고, 실제 `posx`와 1 mm 안쪽으로 맞았다(기준 자세, 비스듬히 움직인 두 자세) [계산].
- 모델로 "같은 X·Y·방향에서 Z만 바꾸는" 관절값을 풀었다.
  - 내리기(−8~−30 mm)는 해가 있었지만 J3가 최대 +19° 움직여야 한다.
  - **올리기는 약 +5 mm가 한계**였다 (팔이 거의 펴진 자세, J3 ≈ 10°).
  - J5 +4°(136.849°)로는 이동이 되지 않았다(사용자 보고). J5 허용 범위가 ±135°로 알려져 있어 그 때문으로 추정한다 [미확인, URDF에는 ±360°].
- 그래서 `s06`은 내리기 4단계, `s07`은 손목 J5만 변경하는 방식으로 정했다. 포즈 도착은 `posx`·`posj`로 목표와 비교해 확인했다 (예: −8 mm 포즈 X +0.01, Y +0.09, Z −8.08 mm).
- `jog_gui`의 Z `−`가 비스듬히 움직인 원인은 **단정하지 못했다**. "꾹 누르기(0.35초 이상) 연속 이동이 작동했다"는 가설을 세웠으나, 톡 두드린 시험에서는 이동 자체가 없어서 확인되지 않았다 [미확인]. B에게 전달할 사항.

## 5. 라벨링 파이프라인

1. **단독 세션 자동 라벨**(`auto_label_single.py`): 클래스는 `class_ranges.txt`, 박스는 정렬 뎁스(바닥 평면 맞춤 → 높은 픽셀의 가장 큰 덩어리). 빈 서랍 배경과의 색 차이로 보강했다. 확대해서 보니 박스가 사방으로 몇 px 넉넉했고, 더 조이면(색 차이만 사용) 흰색·주황색 물체가 잘려서 접었다. **벽에 걸친 `carrot_pen`은 분석 영역(서랍 바닥 안쪽)에서 잘렸다** → 주황·초록 색 분할로 끝까지 따라가게 고침.
2. **Roboflow**: 프로젝트 `ready2go-drawer`(공개, CC BY 4.0 — 무료 플랜이라 비공개 불가, 사용자가 공개 허용 판단). `s01`은 자동 라벨 69장을 올려 사람이 수정. 나머지는 `Auto Label`(`Claude Opus 5.5 (Boxes)`, 53장 예상 비용 0.435 크레딧)로 사전 라벨링 후 확인.
3. **복원**(`import_roboflow.py`): Roboflow가 클래스 번호를 가나다순으로 바꿔 내보내므로 이름으로 `config/yolo_classes.txt` 번호에 재매핑, 파일 이름 접두어로 세션 복원, 이미지는 원본 PNG를 사용. 버전 만들 때 Preprocessing(Auto-Orient, Resize 512×512)과 Augmentation은 모두 껐다(좌표 되돌림 보장).
4. **검증**: 239장 모두 복원, 클래스별 박스 40~60개(검증 5~7개), `s02`는 계획표 1~5번 줄 조합과 정확히 일치, 어긋나 보인 4장은 이미지로 확인해 라벨이 맞음. `build_dataset.py --val s90_val_a s91_val_b` 통과.

## 6. 배운 점

1. **좌표 하나가 이상하면 다른 데이터에서 같은 크기의 값을 찾는다.** 서랍장이 23 cm 떠 있던 것은 TCP 오프셋 228 mm와 1.2 mm 차이였고, 그것이 원인 가설이 되었다. 사용자의 직접 확인이 가설을 확정했다.
2. **분석 영역을 정할 때 경계 조건을 먼저 본다.** 벽에 붙은 물체가 ROI 가장자리에서 잘렸고(`car_key`, `carrot_pen`), 같은 문제가 V2 설계(덩어리 탐색 영역을 `interior_m`으로 정확히 잡을 것)에도 적용된다.
3. **자동으로 더 조이면 오히려 틀린다.** 색 차이만으로 박스를 조이면 배경과 비슷한 물체의 가장자리가 잘렸다. 자동 라벨은 "넉넉하게 + 사람 확인"이 맞았다.
4. **계획과 실제가 다르면 계획표를 정답으로 쓰지 않는다.** `s02`는 조합이 5가지로 줄었고, 이를 라벨과 계획표를 자동 대조해서 발견했다.
5. **원본은 지우지 않고 옮긴다.** 제외한 사진은 `_removed/`로, 이전 자동 라벨은 `labeled_auto_backup/`으로 보관했다.
6. **모델로 풀어 보면 직관이 틀린 이유가 보인다.** 버튼이 비스듬히 움직이는 이유를 코드만으로 추측하다가, 순기구학으로 "팔이 펴진 자세라 올릴 수 없다"는 사실을 확인했다.
7. **검증 범위를 형식과 연동으로 나눠 적는다.** 계약 변경은 형식 테스트가 통과해도 실제 연동은 별도로 확인해야 한다.
8. **추정은 추정이라고 쓴다.** `jog_gui`의 비스듬한 이동은 가설이 시험에서 확인되지 않아 [미확인]으로 남겼다.
