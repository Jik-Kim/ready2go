# ROKEY 웹 대시보드

> [문서] 이 폴더는 이슈 [#112](https://github.com/Jik-Kim/ready2go/issues/112)의 PC·모바일 웹 UI 제안을 검토하기 위한 정적 데모입니다. 현재 실제 음성·Runner·ROS 2·MongoDB·로봇과 연결되어 있지 않으며, P3 또는 `AC-DEMO-01` 완료를 뜻하지 않습니다.

## 1. 이슈 #112에서 웹 UI가 바뀐 과정

이 화면은 처음부터 지금 모습으로 만들어진 것이 아닙니다. 이슈 #112에서 목업과 표시 항목을 검토하면서 다음 순서로 바뀌었습니다.

1. **최초 제안** — PC·모바일에서 같은 작업 상태를 보고, 음성·로봇·카메라 상태와 서랍·준비물·현재 작업을 표시하는 구성을 제안했습니다.
2. **두 번째 목업** — [댓글 6033300834](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6033300834)에서 연결 상태를 작은 블록으로 줄이고, 임시 트레이·별도 복구 영역·이벤트 기록을 제거했습니다. 모바일에는 명령 상세와 서랍 보기를 분리했습니다.
3. **최신 작업 상세 목업** — [댓글 6037139561](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6037139561)에서 명령 접수 배지를 작업 상세 안으로 옮기고, 현재 동작 옆에 `작업 상세 보기 ▾`를 배치했습니다. 실행 단계는 접이식 가로 진행 형태로 변경하고 작업 중단 버튼은 오른쪽에 두었습니다.
4. **연결 구조·관리자 화면 제안** — [댓글 6075167277](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6075167277)에서 브라우저가 서버/브리지를 통해 Runner·온톨로지·기록을 받는 구조를 제안했고, [댓글 6079728121](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6079728121)에서 관리자 검토 패널과 네 개 탭의 화면 구성을 제안했습니다.
5. **현재 구현** — 최신 사용자 대시보드와 관리자 검토 화면을 기존 정적 UI에 반영했습니다. 작업 단계는 PC에서 가로, 모바일에서 세로로 표시합니다. 관리자 버튼은 인증 없이 데모 검토 화면으로 이동하며, 실제 권한 확인이나 보호된 데이터 접근을 수행하지 않습니다.

목업의 물품·시각·실행 순서는 예시입니다. 실제 연동 후에는 서버가 제공한 데이터와 단계만 표시해야 합니다.

## 2. 파일 역할

| 파일 | 역할 | 수정하는 경우 |
|---|---|---|
| `index.html` | 사용자 대시보드와 관리자 검토 화면의 HTML 구조, CSS·JavaScript 진입점 | 화면 영역·탭·접근성 구조를 바꿀 때 |
| `styles.css` | 색상, PC·모바일 배치, 서랍 모양, PC 가로·모바일 세로 진행 단계, 관리자 탭·표 | 목업의 시각 배치나 반응형 기준을 바꿀 때 |
| `demo-data.js` | 사용자 화면과 관리자 화면에서 쓰는 데모 전용 샘플 상태 | 데모 물품·연결 오류·빈 목록·관리자 샘플을 바꿀 때 |
| `app.js` | 샘플 데이터를 표시하고 화면 이동·탭·서랍·상세·데모 중단을 처리 | 렌더링 규칙이나 사용자 상호작용을 바꿀 때 |
| `README.md` | 변화 과정, 실행·접속·실제 연동 교체 지점 설명 | 웹 UI의 사용법이나 연동 방식이 바뀔 때 |

파일 연결 순서는 다음과 같습니다.

```text
index.html
 ├─ styles.css      화면 모양과 반응형 배치
 ├─ demo-data.js    데모 전용 상태 데이터
 └─ app.js          데이터 표시와 버튼 동작
```

## 3. 현재 데이터와 이벤트 구조

`app.js`는 `demo-data.js`가 제공하는 `window.ROKEY_DEMO_DATA`를 읽습니다.

| 화면 | 현재 데이터 경로 |
|---|---|
| 장치 연결 | `connections[].status`, `statusLabel`, `description` |
| 음성 호출 인식 | 음성 연결 항목의 `callStatus`, `callStatusLabel` |
| 들은 말·해석·접수 | `command.heard`, `understood`, `recognition`, `interpretation`, `receipt` |
| 선택한 서랍 | `selectedDrawerId` |
| 실제 작업 위치 | `task.workDrawerId` |
| 등록 물품 | `drawers[].items` |
| 준비물과 완료 수 | `supplies[]`; `status === "delivered"`만 완료로 계산 |
| 현재 작업과 단계 | `task.currentAction`, `currentItemIcon`, `steps[]` |
| 관리자 현재 상태 | `adminReview.current` |
| 관리자 온톨로지·계획·기록 | `adminReview.ontology`, `plan`, `history` |

현재 사용자 이벤트는 다음과 같습니다.

- 서랍 선택: `selectDrawer()`가 조회 대상만 바꾸며 로봇 명령을 보내지 않습니다.
- 작업 상세: `toggleTaskDetails()`가 화면의 상세 영역만 열고 닫습니다.
- 명령·서랍 모바일 패널: `openDialog()`와 `closeDialog()`가 열기·닫기 및 포커스 복귀를 처리합니다.
- 작업 중단: `stopDemoTask()`가 로컬 샘플 상태만 바꿉니다. 실제 중단 API 호출은 없습니다.
- 관리자 화면: `#admin` 해시와 `syncViewFromHash()`로 같은 페이지 안에서 이동하며 인증을 수행하지 않습니다.
- 관리자 탭: `selectAdminTab()`이 선택한 탭 패널만 표시합니다.

## 4. 실제 연동 구조 및 구현 제안

[문서] 현재 웹은 정적 데모입니다. 아래는 [이슈 #112의 연결 구조 논의](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6075167277)와 [관리자 화면 수정안](https://github.com/Jik-Kim/ready2go/issues/112#issuecomment-6079728121)을 바탕으로 현재 구현과 향후 연동 제안을 구분한 것입니다. 실제 연동·인증 구현 또는 담당·계약 승인 완료를 뜻하지 않습니다.

기능의 의미·Phase·수용 기준은 [FR-INT-02](../docs/requirements.md#fr-int-02), [FR-ONT-02](../docs/requirements.md#fr-ont-02), [FR-PLN-02](../docs/requirements.md#fr-pln-02), [FR-LOG-01–02](../docs/requirements.md#fr-log-01), [NFR-SAF-02](../docs/requirements.md#nfr-saf-02)를 참조합니다. 이 장은 정본을 변경하지 않습니다.

### 4.1 상태 데이터 연동

현재 화면은 [`demo-data.js`](demo-data.js)의 샘플 데이터를 사용합니다. 3장의 데이터 경로 표는 현재 데모의 화면 데이터 구조이며 실제 웹 API의 확정된 응답 계약이 아닙니다.

다음은 기존 렌더링을 재사용하는 연결 방법의 제안입니다.

1. 서버의 제공 데이터와 계약을 확인한 뒤 웹 API 어댑터를 구성합니다.
2. `index.html`의 데모 데이터 로딩과 `app.js`의 `window.ROKEY_DEMO_DATA` 참조를 어댑터가 제공하는 데이터로 교체합니다.
3. 어댑터에서 서버 응답을 화면에 필요한 형태로 변환합니다. 기존 구조로 표현할 수 없는 항목은 계약 확인 후 조정합니다.
4. 갱신 방식이 확정되면 수신 데이터에 맞춰 기존 `renderConnections()`·`renderCommand()`·`renderInventory()`·`renderSupplies()`·`renderTask()`를 호출하는 방안을 검토합니다.

표시 의미는 위 요구사항 정본을 참조합니다. 연결 시험에서는 원본 데이터와 화면 표시를 대조하고, 미수신·연결 끊김·GUI 재접속 상황도 확인할 예정입니다. 실제 API 형식과 polling·SSE·WebSocket 중 갱신 방식은 미확정입니다. 연결 구조와 순서는 4.3절을 참고합니다.

### 4.2 작업 중단 연동

현재 `app.js`의 `stopDemoTask()`는 로컬 샘플 상태만 변경하며 실제 중단 API를 호출하지 않습니다.

실제 요청 경로가 합의되면 해당 함수를 서버 요청 및 결과 표시 경로로 교체하는 방안을 제안합니다. 요청 중·실패·처리 결과의 화면 매핑은 실제 응답 계약에 맞춰 결정합니다. 연동 시험에서는 요청 수락과 실제 정지 확인이 각각 어떤 데이터로 표시되는지, 요청 실패 시 화면이 어떻게 갱신되는지 대조합니다.

정지·복구의 의미와 책임 경계는 [NFR-SAF-02](../docs/requirements.md#nfr-saf-02) 및 [FR-SAF-01–03](../docs/requirements.md#fr-saf-01)을 참조합니다. 이 문서 수정으로 로봇 제어·복구·로그 구현을 변경하지 않습니다.

### 4.3 연결 구조 및 연결 순서 — 제안

```text
ROS 상태 토픽 ───┐
온톨로지 정의 ───┼→ 웹 API 서버/ROS 브리지 → PC·모바일 GUI
MongoDB 기록 ────┘
```

브라우저는 웹 API 서버를 통해 데이터를 받는 구성을 제안합니다. 현재 정적 데모에는 웹 API 서버가 없으며, 운영용 관리자 검토 패널의 데이터 요청에는 서버에서 인증·접근 권한을 확인하는 경로가 필요합니다.

연결 순서 제안은 다음과 같습니다.

1. **Runner 실행 상태와 로봇 상태**: `/runner/status`·`/robot_state`의 제공 데이터를 연결하고, 최신 상태 구독 QoS와 GUI 재접속 시 표시를 확인합니다.
2. **음성 및 장치 상태**: 음성 원문·해석·접수·처리 상태와 관측·장치 상태의 제공 경로를 각 담당과 확인해 연결합니다.
3. **관리자 검토 패널**: 범위가 확정되면 실행 기록 조회와 서버가 로드한 온톨로지 정의를 연결합니다. 계획·단계별 근거는 제공 경로를 별도 확인합니다. 위 논의에서 `/planner/plan` 발행과 웹 소비는 미구현으로 보고되었으므로 연결 시 최신 구현을 재확인합니다.
4. **작업 중단**: 합의된 요청 경로와 실제 처리 결과를 연결합니다. 현재 데모 동작의 교체 지점은 4.2절을 참고합니다.

웹 UI·API 서버/ROS 브리지 담당과 코드 경로, API URL·형식, 상태 갱신 방식은 미확정입니다. C의 Runner 상태·기록, E의 음성·상태 의미, A/B의 관측·장치 자료 제공 경로를 협의할 예정입니다. 이 순서는 계획이며 실제 연동 완료를 뜻하지 않습니다. 현재 인터페이스는 [interfaces.md](../docs/interfaces.md), 계약 변경 절차는 [AGENTS.md](../AGENTS.md)를 참조합니다.

### 4.4 관리자 검토 화면 — 현재 데모와 향후 연동

현재 관리자 버튼은 인증 없이 검토 화면으로 이동하는 데모용 진입 기능입니다.
이 진입 기능에는 관리자 인증 및 서버 API 접근 제어가 구현되어 있지 않으며,
화면 진입이 관리자 권한 확인을 의미하지 않습니다.
실제 관리자 데이터 연동·운영 전 서버 인증과 접근 제어를 연결해야 합니다.

현재 구현은 같은 정적 페이지 안에서 `#admin`으로 전환되며, 현재 상태·온톨로지·계획 근거·실행 기록 중 선택한 탭 하나만 표시합니다. 현재 상태와 온톨로지·실행 기록의 값은 `demo-data.js`의 명확히 표시된 샘플이고, 계획 근거는 제공 경로가 없어 미연동으로 표시합니다. 과거 실행 샘플은 현재 상태 판단에 사용하지 않습니다.

실제 연동 시에는 `app.js`의 관리자 렌더링 함수는 유지하고 `demo-data.js`의 `adminReview` 공급부를 서버 응답 어댑터로 교체합니다. Runner 저장 상태와 실제 관측 결과는 서버 응답의 출처를 그대로 표시해야 하며, 오류 데이터가 없으면 오류 없음으로 단정하지 않습니다. 온톨로지는 서버가 로드한 원본 정의, 실행 기록은 승인된 기록 조회 경로, 계획 근거는 실제 제공 경로에서만 받아야 합니다.

## 5. 정적 데모 실행

프로젝트 PC에서 `ready2go` 저장소 루트로 이동한 뒤 다음 명령을 실행합니다.

```bash
python3 -m http.server 4173 --directory web
```

이 명령은 파일을 보여 주는 임시 정적 서버입니다. 실제 웹 API·ROS 브리지·관리자 인증 서버를 실행하지 않습니다. 터미널을 닫거나 `Ctrl+C`를 누르면 서버가 종료됩니다.

같은 PC에서는 다음 주소로 접속합니다.

```text
http://localhost:4173
```

## 6. 휴대폰과 다른 PC에서 접속

### 6.1 서버 PC의 주소 확인

서버를 실행한 PC에서 새 터미널을 열고 다음 명령을 실행합니다.

```bash
hostname -I
```

여러 주소가 나오면 보통 와이파이·유선 LAN 주소를 사용합니다. `172.17.x.x`처럼 Docker가 만든 주소는 사용하지 않습니다. 아래 `172.24.1.176`은 기존 접속 안내의 예시입니다. 현재 환경에서 확인한 서버 PC 주소로 바꿔 사용합니다.

### 6.2 휴대폰

휴대폰을 서버 PC와 같은 와이파이에 연결하고 브라우저에서 다음 형식으로 접속합니다.

```text
http://서버_PC_IP:4173
```

주소를 적용한 예시는 다음과 같습니다.

```text
http://172.24.1.176:4173
```

화면 폭에 따라 모바일 배치로 자동 전환되며 별도의 `/mobile` 주소는 없습니다.

### 6.3 다른 PC

다른 PC도 서버 PC와 같은 네트워크에 연결한 뒤 같은 주소를 사용합니다.

```text
http://172.24.1.176:4173
```

접속되지 않으면 다음을 확인합니다.

- 서버 PC 터미널에 `Serving HTTP on 0.0.0.0 port 4173`이 표시되는지
- 두 장치가 같은 와이파이·유선망에 있는지
- 방문자망·기관망에서 장치 간 통신을 차단하지 않는지
- 서버 PC 방화벽이 TCP 4173 포트를 차단하지 않는지

## 7. 테스트용 데모 시나리오

화면 버튼을 추가하지 않고 URL로 예외 상태를 확인할 수 있습니다.

```text
http://localhost:4173/?scenario=long
http://localhost:4173/?scenario=empty
http://localhost:4173/?scenario=error
```

각각 긴 물품명, 빈 목록, 연결 오류의 화면 넘침을 확인하기 위한 데모입니다. 관리자 화면은 각 시나리오에서도 열 수 있지만 인증 시험은 포함하지 않으며, 화면 진입은 권한 확인을 뜻하지 않습니다.
